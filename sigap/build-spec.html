SIGAP System architecture Research 3 Oct 2026

SIGAP, the system as it stands

What runs, what talks to what, and which of it works. Twelve agents, thirty-one tools, one database, two processes.

Every number on this page was read out of the repository rather than out of a plan: agents/definitions.py for the roster, core/registry.py for the tools, api.py for the route table, app/ for the interface. Where something is named but not wired, §12 says so instead of leaving it implied.

01

Five things you start

Two processes carry the system. Three more are run by hand or on a schedule. Nothing is containerised, nothing is deployed, and there is no queue between them: the boundary is one HTTP call and one SQLite file.

RunListensJob
cd sigap/agent && python3 api.py :8787 The agent service. 23 routes, the standard library only, SQLite at data/sigap.db. Owns the roster, the runs, the actions, the approvals and the conversations.
npm run dev :3000 The interface. Next.js 16.3.4 on Turbopack, 14 pages. Reads through one proxy and never holds data of its own.
python3 sender.py — The write-out. Run on a schedule. Takes approved actions and posts them to SAP.
python3 signals/bmkg.py — The live signal. Reads data.bmkg.go.id no credential, no registration and POSTs anything worth handling.
python3 manage.py … — The CLI. check · seed · docs · secret · user
The one line between the two processes

app/api/sigap/[...path]/route.ts forwards every page request to http://127.0.0.1:8787 and attaches the session token from the httpOnly cookie. The browser never reaches :8787 directly, so the token is never in page code and never in a response body. If the agent service is down, every page renders the same 503 with the command to start it.

04

How a disruption is handled

graph.run() is the orchestration loop. Arya is not a router with a fixed pipeline: she is handed the event and the ten ask_<code> tools, and decides the order from what the last specialist found. 

POST /events
  → store.record_event                events table
  → store.start_run                   runs table, status running, mode: guided | autonomous
  → _handle in a thread
      graph.run(event, report)
        → Arya, tools = ask_<code> ×10 + her own detect_disruption
        → she calls ask_impact, one at a time
            → _tool_loop for that specialist, up to 8 rounds
                → registry.run(name, args)
                    → tools/fetcher.py → clients/sap_s4.py → SAP OData
                    → no key? → fixtures/, origin MODELLED
                → every finding lands on the Board with its origin
        → report() writes one row per turn     steps table
        → she calls ask_compliance next
            → Kira vetoes in Python arithmetic, not in the prompt
        → she calls ask_simulation
            → Tara calls engine/simulate.py  deterministic, no model
        → she stops when the evidence is enough → status done
  → store.close_run(run_id, "done", recommendation, cost_idr)
  → an exception is written to the run as "failed", never swallowed

If AWS_REGION is empty which is today

POST /events
  → mode = "guided"
  → store.close_run(rid, "held", decision={
        "reason": "AWS_REGION is not set. The agent team cannot reason.
                   No decision was made." })        the run stops here

The event is recorded, the run exists, the queue shows it as held. What does not happen is any reasoning. The same guard raises ModelNotReady in graph.client() and returns 503 from POST /agents/{code}/ask.

05

Asking one agent directly

Two entry points into the same loop. Conversation asks Arya, who routes. An agent page asks that specialist alone same tools, same board, no lead deciding the turn order. Used from /chat and from /agents/{code}. 

POST /agents/{code}/ask     {question, conversation_id?}
  → _user(headers)          identity from the token only, never from the body
  → conversation_id must belong to that user  an id is a claim, not proof
  → graph.ask_specialist(code, question, history)
      → _tool_loop, up to 8 rounds
      → returns answer, tools_used, board+origins, cost_idr
  → store.start_conversation  only if there is an answer to store
  → conversations + messages tables

History is replayed as model turns, last 12 messages, agent errors dropped because they are not answers. A failed ask leaves no empty conversation behind it.

06

The arithmetic

Four modules do the reasoning that must not be delegated to a model. They are plain Python, they have their own demo() entry points, and no credential is needed to run them.

ModuleWhat it decidesCalled by
engine/forecast.py Daily consumption as a moving variable seasonal indices over the consumption history, not the master-data constant. This is what turns "the plant burns 9.2 t/day" into 10.33 and widens the gap from 82.8 t to 118.4 t. forecast_demand, the cover projection
engine/matching.py Judges a transfer from both ends: does the source plant drop below its own floor after giving the stock away? find_internal_transfers, assess_transfer
engine/simulate.py Arrival dates, days of cover, and the cost of what survived the veto. Refuses to emit a rupiah figure when an input on the critical path is not LIVE / CACHED / DERIVED a missing number stops the calculation rather than becoming a confident guess. simulate_scenario, project_cover
engine/audit.py Reads everything the system can see and reports what is wrong with the data itself: negative stock, safety floors below zero, POs in the past, missing consumption. No model involved, so any finding can be recomputed from the same rows. GET /audit → /audit
Kira's veto is arithmetic

check_local_constraints is a registered tool that runs in Python and writes a Result with an origin. The model is not asked to agree with it. That is also why Bedrock Guardrails was declined: a guardrail filters model output, this never reaches the model to be filtered.

07

Where a number comes from

core/provenance.py. Every tool returns a Result, never a bare value, and every result carries one of five origins. The label survives the whole way to the screen.

OriginMeansMay back a rupiah figure?
LIVEStraight from SAP or an official APIyes
CACHEDWas live once, carries its timestampyes
DERIVEDComputed from something liveyes
MODELLEDCompany profile or fixture, labelled in the openno
MISSINGThe lead stops here rather than guessingno

The read path, in order

any read tool
  → tools/fetcher.pull(fixture_entity, sap_service, sap_entity)
      → sap_s4.available()?   SAP_API_KEY set
           yes → GET OData, filter   → LIVE
                exception        → MISSING with the exception as the note
           no  → fixtures/ningbo_scenario.json  → MODELLED
  → an uploaded CSV of the same entity layers over both, origin becomes CACHED

The fallback is never hidden. The origin is shown next to every figure, the dashboard reports the weakest origin in play, and the calculator refuses the figure outright when it is not trusted. Guessing would mean laundering generated rows as real ones, which is the thing this system exists to prevent which is also why the uploader makes you say whether a file is master data or a sample.

You can uploadEntity
Stock on hand per material per plantMaterialStock
Open purchase orders and ETAsPurchaseOrder
OEM sales commitmentsSalesOrder
Which finished goods a material feedsBillOfMaterial
Alternate sources for a materialAlternateSource

Five entities, csv.DictReader, numbers coerced back to numbers, rejected with a reason rather than silently dropped. Uploading is what moves a domain from MODELLED to CACHED.

Identity, approval, and the write

The four roles

RoleMay approve up to
plannerRp 0 read only
buyerRp 500,000,000
procurement_leadRp 10,000,000,000
adminRp 10,000,000,000

A person approves

POST /actions/{id}/decision     {decision, note}
  → identity.from_token          role comes from the token, never the body
  → u.may_approve(payload.cost_idr)   403 with "escalate to procurement_lead" if not
  → store.decide_action         one shot  a decided action never changes again
                              approvals records who, what role, when

core/identity.py signs and verifies the token itself. The comment in the source is the design: this used to trust a role in the request body, which meant anyone could claim any role.

An approved action reaches SAP

python3 sender.py                run on a schedule
  → SAP_API_KEY not set? → "Nothing sent." and stop
  → for each action with status = approved
      → TARGETS[kind] → service + entity
      → sap_s4._csrf_token(service)   fetch
      → sap_s4.post(service, entity, payload, idempotency_key)
      → store.mark_sent(sap_reference)
      on failure status is NOT changed  stays approved, retried, key prevents a double order
Three write targetsServiceEntity
draft_poAPI_PURCHASEREQ_PROCESS_SRVA_PurchaseRequisitionHeader
stock_transferAPI_STOCK_TRANSFER_SRVA_StockTransfer
create_sourcing_eventAPI_SOURCING_PROJECT_SRVA_SourcingProject
What can and cannot go out without a person

Only a stock transfer under Rp 50 million can touch SAP on its own and only when SAP_API_KEY is set. A draft PO always waits for a buyer. A sourcing event never goes autonomous whatever its value. A safety-stock change is a policy edit, so it always escalates and the sender will never send it: a person applies it.

idempotency_key is a hash of the action's content, not a counter. The same action raised twice returns the existing record with repeated: true instead of becoming a second PO.

Wired, and not wired

Stated plainly so nobody discovers it during a demo.

Status
Roster, registry, promptsComplete. 12 agents, 31 tools registered and claimed with no gap either way, 12 prompts written
Route table, store, identity, approvalsWorking. 23 routes respond; the proxy, login, queue, audit, log and roster all render against a running service
Provenance and the trust checkWorking. Fixtures are labelled MODELLED on screen and refused by the calculator
The engine forecast, matching, simulate, auditWorking. Deterministic, each with its own demo(), no credential required
AWS_REGIONEmpty. graph.py has never run against a real model. Runs are recorded as held and /agents/{code}/ask returns 503. Everything above is plumbing that a scripted client proves, and judgement that nothing proves yet
SAP_API_KEYNot set. All reads fall back to fixtures, labelled MODELLED; sender.py sends nothing
Bram's and Prita's action recordFixed. tools/execution.py took its run id from a _run_id argument nothing ever passed, so it fell back to run_detached and with foreign keys on the insert raised IntegrityError: FOREIGN KEY constraint failed reproduced against create_draft_po. The run id now comes from registry.current_run(), a ContextVar bound by api._handle around graph.run and reset when the handling ends, so one run cannot inherit another's id. Outside a handling there is no run to attach to, and raise_action() refuses with a note rather than writing a row nobody could approve
