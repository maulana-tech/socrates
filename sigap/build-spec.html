SIGAP Build spec Research 29 Sep 2026

Building SIGAP on AWS and SAP

What runs where, which service does which job, and what is wired versus what is only named.

AWS-PLAN.md has the order of the AWS work and the reasoning behind the Runtime decision. DATA-SOURCES.md has where each kind of data comes from and how it was verified. This is the wiring: the service list on both sides, and the paths a request takes through them.

01

The case, in one page

PT Karya Presisi Nusantara, a Tier-1 automotive component maker. Two plants, KRW1 Karawang and SBY1 Surabaya. 340 active materials, 61% of raw-material value imported, mostly through Tanjung Priok. The OEM contract requires TKDN of at least 40%; the portfolio sits at 38.2%.

A typhoon closes Ningbo-Zhoushan for six days. PO 4500018872, 120 t of M-4471 aluminium alloy ingot, slips from 14 September to 22 September. KRW1 holds 84 t and the master data says it burns 9.2 t a day, so it empties on 13 September. Nine days with no material, against three OEM sales orders worth Rp 2.14 billion and a late penalty of 0.5% a day capped at 10%.

What the system does with that

  1. Works out what the disruption actually hits, and how deep the hole is
  2. Assembles the ways out: air freight, a local supplier, a transfer from SBY1
  3. Strikes the ones that breach TKDN or need an import licence that will not arrive in time. This veto is arithmetic, not a prompt, and cannot be overturned on cost
  4. Prices what is left and recommends one
  5. Executes it into SAP once someone with the authority approves, or on its own authority below Rp 50 million
  6. Watches until the goods land
Three things about the case are the product

The plant does not run at 9.2. It has run at 10.33 for a month. The gap is 118.4 t, not 82.8 t, and the 85 t air freight option does not bridge it. engine/forecast.py is what finds that.

The transfer from SBY1 breaks SBY1. Moving 55 t drops it from 18.0 to 12.3 days, under its own 14 day floor, emptying 16 September while its own PO lands 24 September. engine/matching.py judges a transfer from both ends.

Every figure says where it came from. LIVE, CACHED, DERIVED, MODELLED, MISSING. The calculator refuses to produce a rupiah figure from untrusted inputs rather than producing a confident wrong one.

Under review, found 29 September

AWS for SAP MCP Server

A container AWS ships at no cost, running on AgentCore Runtime, that exposes SAP OData as MCP tools with catalog discovery and OAuth 2.0 already handled. It did not exist when clients/sap_s4.py was written. See §5: it addresses the auth problem directly. The research page has the detail.

04

SAP: the surface we actually touch

Connector is clients/sap_s4.py. Base URL defaults to https://sandbox.api.sap.com, overridable with SAP_BASE_URL.

Everything routes through tools/fetcher.py, which tries SAP first and falls back to fixtures/ when there is no key. The fallback is never hidden. The origin becomes MODELLED, which shows on screen and fails the calculator's trust check.

05

Auth, and the thing that will bite

clients/sap_s4.py sends an APIKey header. That is the SAP Business Accelerator Hub sandbox scheme, and it works today.

A real customer system does not accept it. S/4HANA Cloud wants a communication user or OAuth 2.0 through a BTP destination.

A correction to DATA-SOURCES.md §1

"Change the base URL and the key, the code does not change" is optimistic. The base URL changes, the key changes, and the authentication scheme changes. It is one function, sap_s4.get(), so it is a small change, but it is a change and it should be written down rather than discovered on the day.

This is exactly what the AWS for SAP MCP Server already solves, and it is the strongest argument for evaluating it before we write more connector code.

06

The three paths through the system

A disruption arrives

signals/bmkg.py, or POST /events
  → store.record_event          events table
  → store.start_run             runs table, status running
  → graph.handle in a thread
      → Arya picks a specialist, calls ask_<code>
      → that specialist calls its tools
          → tools/fetcher.py → clients/sap_s4.py → SAP OData
          → no key? → fixtures/, origin MODELLED
      → every result lands on the Board with its origin
      → store.save_step          steps table, one row per turn
      → Kira may veto. Arithmetic, not judgement
      → engine/simulate.py prices what survives
  → store.record_action          idempotency_key, so a retry never doubles a PO
  → under Rp 50m: status sent. Over: status pending

A person approves

POST /actions/{id}/decision
  → identity.from_token          identity ONLY from the token, never the body
  → user.may_approve(value)      role cap, server side
  → store.decide_action          one shot; a decided action never changes again
                                 approvals table records who, what role, when

An approved action reaches SAP

sender.send_approved
  → for each approved, unsent action
  → sap_s4._csrf_token(service)  fetch
  → sap_s4.post(service, entity, payload)
  → store.mark_sent(sap_reference)

Guards that hold regardless of what any model says: MAX_SPECIALIST_ROUNDS = 8, MAX_LEAD_ROUNDS = 14, MAX_SECONDS_PER_EVENT = 600, CFG.cost_cap_per_event_idr.

What moving to Runtime changes

Less than it sounds, which is the point of having owned the loop.

FileChange
graph.pyEntry point gets the AgentCore Runtime decorator. The loop itself does not change

core/trace.pyAlso emits OTel spans. Keeps writing steps, because that table is the approval record, not a debug log
core/store.pyUnchanged. SQLite moves to Postgres when this is multi-tenant, not before
core/identity.pyUnchanged, deliberately
clients/sap_s4.pyDecide first. Either gains OAuth, or is replaced by the AWS for SAP MCP Server. Decide before writing more of it
api.pyUnchanged. It is the interface's bridge, not the agent runtime
